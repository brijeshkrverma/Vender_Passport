Critical — deploy blockers

CriticalCore workflow stage 5 par permanently toot jaata hai

backend/modules/audits/audit.service.js:16-21 ka nextStatus() stage 5 se aage 'In Progress' return karta hai — jo audit.model.js:19 ke status enum me hai hi nahi. Mongoose save par validation error deta hai.

Maine model validation actually chalake confirm kiya:

stageIdx  4 -> status: Auditor Assigned  ok
stageIdx  5 -> status: In Progress       *** INVALID (save fails)
stageIdx  6 -> status: In Progress       *** INVALID (save fails)
...
stageIdx 10 -> status: In Progress       *** INVALID (save fails)
stageIdx 11 -> status: Closed            ok

Matlab koi bhi audit Execution se aage nahi jaa sakta. Evidence Review, Findings, Corrective Actions, Verification, Report — 12 me se 6 stages API se reachable hi nahi hain. Upar se seed data me stageIdx: 25 jaisi values hain jabki max valid index 11 hai.

Kyun matter karta hai: ye product ka core promise hai. Fix ek line ka hai (return LIFECYCLE[stageIdx]), par jab tak nahi hota, koi bhi audit complete nahi ho sakta.

CriticalPublic register endpoint se koi bhi Super Admin ban sakta hai

backend/modules/auth/auth.routes.js:8-15 me register schema:

role:  z.string(),   // koi enum nahi — kuch bhi accept
orgId: z.string(),   // client jo bheje wahi

User model ka enum 'Super Admin' allow karta hai, aur middleware/tenant.js:7-13 Super Admin ke liye org check poora bypass kar deta hai. Toh ek curl se {"role":"Super Admin","orgId":"ORG-101"} bhejne par attacker us tenant ka — balki saare tenants ka — full admin ban jaata hai. orgId guess karna bhi trivial hai: frontend ka default hi ORG-101 hai.

Fix: self-signup roles ki allow-list (Super Admin / Organization Admin kabhi nahi), aur orgId client se lene ke bajaye server-side derive ya invite-token se resolve karo.

CriticalAudit product hai, par audit trail hi nahi hai

Poore backend me koi activity/audit-log collection nahi. settings.auditLog sirf ek boolean toggle hai jiske peeche kuch implement nahi. /audit-trail page StubPage hai. Saath me har module findOneAndDelete use karta hai — hard delete, na soft delete, na versioning, na change history.

Business impact: finding ko chupke se edit ya delete karke koi nishaan nahi chhodna — matlab is system ki output ko koi certification body, regulator ya SOC 2 auditor evidence maanega hi nahi. ISO 27001, SOC 2, 21 CFR Part 11 — sab append-only record maangte hain. Ye feature gap nahi, product ki credibility ka issue hai.

High — audit domain integrity

HighEvidence apna hi upload karne wala verify kar sakta hai

modules/evidence/evidence.routes.js:24 me PATCH /:id/verify saare 12 roles ko allowed hai — Employee aur External Company User bhi shamil. Yaani vendor apna hi evidence "Verified" mark kar sakta hai. Auditor bhi jo khud upload kare wahi verify kar de.

Audit independence ka pura point yahi hai. Verify karne wala uploader se alag hona chahiye, aur role Reviewer tak limited hona chahiye.

HighChain of custody khaali save hoti hai

evidence.controller.js:63 service ko req.user.sub bhejta hai, par middleware/auth.js:28 me sub field set hi nahi hota — wahan userId hai. Result: verifiedBy hamesha undefined store hota hai.

"Kisne verify kiya" — audit evidence ka sabse basic metadata — record hi nahi hota. Aur ye chup-chaap fail hota hai, koi error nahi.

HighSegregation of duties enforce nahi hoti

audit.service.js ka assignAuditor kisi ko bhi assign kar deta hai — koi check nahi ki auditor auditee na ho, ya assign karne wala khud ko lead na bana le. Audit independence ke rules code me kahin encode nahi hain.

Ye wahi cheez hai jiske liye log audit software kharidte hain — manual process me ye rule paper par hota hai, software me enforce hona chahiye.

HighBackend business logic ka test coverage practically zero

tests/integration/ aur tests/fixtures/ bilkul khaali directories hain. Sirf 1 unit test file (helpers.test.js) aur 11 Playwright e2e specs hain.

Isi wajah se lifecycle wala bug aur RBAC gaps release tak pahunch gaye. Ek basic integration test advance ko stage 5 tak chalake turant pakad leta.

Business model ke issues

Medium"Vendor Passport" ka core idea implement hi nahi hua

Product ka naam aur pitch cross-company trust sharing ka hai — vendor apna passport customers ke saath share kare. Par data model strict single-org isolation enforce karta hai. targetOrgId (audit.model.js:15) aur vendorOrgId (vendor.model.js:14) sirf declare hain — kisi bhi query me use hi nahi hote. /exchange page StubPage hai.

Second-party / third-party audit me jis org ka audit ho raha hai, wo apna hi audit dekh nahi sakti. Jo cheez bechni hai, wahi missing hai.

MediumCA / Consultant role architecturally impossible hai

Iska pura business multiple clients handle karna hai — "Client Portfolio" page bhi isi liye bana hai. Par uska JWT ek hi orgId rakhta hai aur tenantIsolation cross-org access block karta hai.

Ya toh multi-org membership model chahiye (user ↔ org many-to-many with per-org role), ya ye role kabhi kaam nahi karega. Ye ek schema-level decision hai, patch nahi.

MediumMonetization ka koi primitive hi nahi

subscription, plan, seat, licence, invoice, payment — poore backend me kuch nahi mila (grep me sirf "actionPlan"/"Planning" match hue). Register page par likha hai "free for vendors, always" par paid side ka koi concept hi nahi: na plan tiers, na seat limits, na usage metering, na org-type based feature gating.

Day-1 blocker nahi hai, par abhi ye product revenue collect kar hi nahi sakta. Aur pricing model baad me retrofit karna schema me deep changes maangta hai.

Jo genuinely achha hai

Ye kehna zaroori hai — foundation kamzor nahi hai:

  • Modular structure (routes → controller → service → model) har module me consistent
  • Zod validation har mutating route par, proper error classes aur central error handler
  • RBAC aur tenant isolation reusable middleware ke roop me — pattern sahi hai
  • bcrypt 12 rounds, JWT with jti + Redis blacklist, refresh token rotation
  • Helmet + CSP, global aur login-specific rate limiting
  • File upload par extension allowlist, 25MB limit, randomized filenames (path traversal safe)
  • orgId par proper compound indexes — scale ke liye sochke banaya gaya hai
  • 21 modules ka consistent API surface — feature breadth genuinely badi hai
Problem execution gaps me hai, design me nahi. Yahi achhi khabar hai — jo toota hai wo mostly fixable hai, rewrite nahi chahiye (do exceptions: audit trail aur multi-org model, jo naye schema maangte hain).
